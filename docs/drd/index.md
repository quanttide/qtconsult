# 数据需求文档

## 咨询服务看板

### 业务场景

顾问在项目交付过程中需要在一个看板上完成四件事：记录调研发现、提炼洞察、制定策略、追踪执行。看板以 OODA（Observe-Orient-Decide-Act）循环组织四个数据板块。

### 数据需求

#### 1. 调研发现数据

**用途**：记录客户说的"要什么"（业务需求）和"实际是什么"（技术现实），形成决策依据。

**数据来源**：
- 顾问手动录入（访谈纪要、调研记录）
- 客户确认交互（勾选确认 / 驳回）
- 导入（历史调研报告结构化导入）

**数据项**：

| 数据项 | 说明 | 录入方式 | 示例 |
|--------|------|---------|------|
| 卡片标题 | 核心事实的一句话概括 | 顾问录入 | 战略转型 · 商家赋能 |
| 详细描述 | 事实的具体展开 | 顾问录入 | 从"做大平台订单"转向"帮商家拉流量、提营收" |
| 分类标签 | 业务理想 / 现实状况 | 顾问选择 | 业务理想 |
| 来源 | 从哪次接触得来 | 顾问选择+录入 | 模拟访谈 · 5月15日 |
| 日期 | 记录日期 | 自动 | 5月15日 |
| 确认状态 | 客户是否认可事实准确 | 客户操作 | 待确认 → 已确认 |

#### 2. 洞察分析数据

**用途**：从调研发现中提炼矛盾、根因和影响，连接"事实"与"策略"。

**数据来源**：
- 顾问基于调研发现手动提炼
- 关联到具体调研卡片作为证据

**数据项**：

| 数据项 | 说明 | 录入方式 |
|--------|------|---------|
| 洞察标题 | 矛盾或结论陈述 | 顾问录入 |
| 关联证据 | 引用了哪些调研卡片 | 顾问关联 |
| 根因 | 问题的根本原因 | 顾问分析 |
| 影响 | 不处理的后果 | 顾问分析 |
| 聚类 | 所属分析维度 | 顾问选择 |

#### 3. 决策方案数据

**用途**：基于洞察生成可执行的策略方案，供客户选择。

**数据来源**：
- 咨询团队制定
- 客户反馈（倾向选择 + 条件备注）

**数据项**：

| 数据项 | 说明 | 录入方式 |
|--------|------|---------|
| 方案名称 | 方案的一句话概括 | 团队录入 |
| 优势 | 为什么选这个方案 | 团队录入 |
| 概要 | 分阶段执行计划 | 团队录入 |
| 资源需求 | 人力、时间、费用 | 团队录入 |
| 关键假设 | 方案成立的前提条件 | 团队录入 |
| 客户倾向 | 客户是否倾向此方案 | 客户操作 |
| 客户备注 | 客户填写的顾虑或条件 | 客户录入 |

#### 4. 执行任务数据

**用途**：追踪方案落地过程中的具体任务。

**数据来源**：
- 基于决策方案自动生成
- 手动新增/调整

**数据项**：

| 数据项 | 说明 | 录入方式 |
|--------|------|---------|
| 任务名称 | 做什么 | 团队录入 |
| 状态 | 待开始/进行中/已完成/受阻 | 团队更新 |
| 负责人 | 谁做 | 团队指定 |
| 时间计划 | 起止日期 | 团队录入 |
| 进度 | 百分比 | 自动/手动 |
| 受阻原因 | 卡在哪 | 受阻时填写 |
| 关联策略 | 属于哪个方案 | 关联选择 |

### 数据关系

```
调研发现 → 引用 → 洞察分析 → 支撑 → 决策方案 → 分解 → 执行任务
```

- 一条洞察可引用多条调研发现
- 一条决策方案可由多条洞察支撑
- 一项执行任务归属于某个决策方案
- 调研发现需客户确认后才进入分析环节

### 数据管理规则

| 规则 | 说明 |
|------|------|
| 数据归属 | 按项目隔离，不同项目数据不可见 |
| 版本记录 | 洞察和决策修改需保留历史版本 |
| 删除策略 | 调研发现删除后不影响已关联洞察（断开链接） |
| 导入导出 | 支持 JSON 格式导出 |
| 确认机制 | 调研发现需客户确认后才能用于正式报告 |
