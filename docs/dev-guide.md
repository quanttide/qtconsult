# 开发指南

汇总业务背景、看板与数据设计、交互设计、项目计划、验收用例与存储运维，按主题组织。

> 各节沿用成文时的表述。看板阶段命名此后有过调整：现行的需求澄清、调研分析、决策方案、执行跟踪对应文中的 Observe、Orient、Decide、Act。

## 业务与产品背景

### 咨询服务方

最主要的困难，是如何收集和整理来自一线的信息，再汇总成一个框架。

目前采取「日志 + 简介」的信息架构：日志忠实按时间先后完整记录所有信息，尽可能把散乱信息收进业务系统；简介从中提取关键信息放进正式看板。整理成简介的过程中，最大困难是信息整理和提炼——AI 会乱编信息架构，人类理解不了，人类制定框架又不全面。信息要充分用起来，还得不断与人沟通确认、达成共识。

### 客户

客户最大的顾虑首先是：花出去的钱到底能干什么，有没有白花。

其次是对咨询公司的不信任，例如价格是否透明。客户侧还有什么问题，仍需继续探究，目前想得尚不完整。

### 产品核心

产品要做一个信息看板，其结构可以动态维护：具体信息、信息结构乃至展示方式都有一整套标准化积木，方便甲乙双方以及乙方内部根据理解不断调整。

## 看板结构

看板是咨询项目的工作空间，按 OODA 循环分为四个列表展示不同类型的信息卡片。

| 列表 | 卡片类型 | 说明 |
|------|----------|------|
| Observe | 调研卡 | 记录客户的事实与发现 |
| Orient | 洞察卡 | 提炼矛盾、根因与影响 |
| Decide | 策略卡 | 制定可执行方案 |
| Act | 任务卡 | 追踪落地执行 |

### 卡片

卡片是看板的基本单元，字段分内置与自定义两类。

| 标识 | 中文 | 类型 | 说明 |
|------|------|------|------|
| title | 标题 | string | 卡片名称 |
| description | 描述 | string | 展开说明 |
| category | 系统分类 | string | 系统内置概念，如 ideal / reality |
| types | 问题领域 | string[] | 问题所属领域，如战略技术断层、数据基建 |
| tags | 标签 | string[] | 灵活标记，支持多标签 |
| date | 日期 | date | 支持单日期和起止日期 |
| assignee | 负责人 | string | 执行人 |
| upstream | 上游卡片 | Card[] | 信息来源引用 |

自定义字段按具体咨询项目动态配置业务字段，如根因、影响、优势、资源需求、客户倾向、进度等。

### 列表与卡片类型

列表中存放对应类型的卡片：

- Observe 列表：存放调研卡，通过 `category` 字段区分业务理想（`ideal`）与技术现实（`reality`）
- Orient 列表：存放洞察卡，从调研卡中提炼分析结论，通过「来源卡片」引用调研卡
- Decide 列表：存放策略卡，基于洞察生成方案，通过「来源卡片」引用洞察卡
- Act 列表：存放任务卡，分解策略为执行事项，通过「来源卡片」引用策略卡

卡片之间形成信息链路：

```text
调研卡（Observe）→ 洞察卡（Orient）→ 策略卡（Decide）→ 任务卡（Act）
```

## 数据需求

### 业务场景

顾问在项目交付过程中需要在一个看板上完成四件事：记录调研发现、提炼洞察、制定策略、追踪执行。看板以 OODA（Observe-Orient-Decide-Act）循环组织四个数据板块。

### 调研发现数据

用途：记录客户说的「要什么」（业务需求）和「实际是什么」（技术现实），形成决策依据。

数据来源：顾问手动录入访谈纪要与调研记录；客户勾选确认或驳回；历史调研报告结构化导入。

| 数据项 | 说明 | 录入方式 | 示例 |
|--------|------|---------|------|
| 卡片标题 | 核心事实的一句话概括 | 顾问录入 | 战略转型 · 商家赋能 |
| 详细描述 | 事实的具体展开 | 顾问录入 | 从「做大平台订单」转向「帮商家拉流量、提营收」 |
| 分类标签 | 业务理想 / 现实状况 | 顾问选择 | 业务理想 |
| 来源 | 从哪次接触得来 | 顾问选择 + 录入 | 模拟访谈 · 5月15日 |
| 日期 | 记录日期 | 自动 | 5月15日 |
| 确认状态 | 客户是否认可事实准确 | 客户操作 | 待确认 → 已确认 |

### 洞察分析数据

用途：从调研发现中提炼矛盾、根因和影响，连接「事实」与「策略」。

数据来源：顾问基于调研发现手动提炼，并关联具体调研卡片作为证据。

| 数据项 | 说明 | 录入方式 |
|--------|------|---------|
| 洞察标题 | 矛盾或结论陈述 | 顾问录入 |
| 关联证据 | 引用了哪些调研卡片 | 顾问关联 |
| 根因 | 问题的根本原因 | 顾问分析 |
| 影响 | 不处理的后果 | 顾问分析 |
| 聚类 | 所属分析维度 | 顾问选择 |

### 决策方案数据

用途：基于洞察生成可执行的策略方案，供客户选择。

数据来源：咨询团队制定，客户反馈倾向选择与条件备注。

| 数据项 | 说明 | 录入方式 |
|--------|------|---------|
| 方案名称 | 方案的一句话概括 | 团队录入 |
| 优势 | 为什么选这个方案 | 团队录入 |
| 概要 | 分阶段执行计划 | 团队录入 |
| 资源需求 | 人力、时间、费用 | 团队录入 |
| 关键假设 | 方案成立的前提条件 | 团队录入 |
| 客户倾向 | 客户是否倾向此方案 | 客户操作 |
| 客户备注 | 客户填写的顾虑或条件 | 客户录入 |

### 执行任务数据

用途：追踪方案落地过程中的具体任务。

数据来源：基于决策方案自动生成，或手动新增、调整。

| 数据项 | 说明 | 录入方式 |
|--------|------|---------|
| 任务名称 | 做什么 | 团队录入 |
| 状态 | 待开始/进行中/已完成/受阻 | 团队更新 |
| 负责人 | 谁做 | 团队指定 |
| 时间计划 | 起止日期 | 团队录入 |
| 进度 | 百分比 | 自动/手动 |
| 受阻原因 | 卡在哪 | 受阻时填写 |
| 关联策略 | 属于哪个方案 | 关联选择 |

### 数据关系

```text
调研发现 → 引用 → 洞察分析 → 支撑 → 决策方案 → 分解 → 执行任务
```

- 一条洞察可引用多条调研发现
- 一条决策方案可由多条洞察支撑
- 一项执行任务归属于某个决策方案
- 调研发现需客户确认后才进入分析环节

### 数据管理规则

| 规则 | 说明 |
|------|------|
| 数据归属 | 按项目隔离，不同项目数据不可见 |
| 版本记录 | 洞察和决策修改需保留历史版本 |
| 删除策略 | 调研发现删除后不影响已关联洞察（断开链接） |
| 导入导出 | 支持 JSON 格式导出 |
| 确认机制 | 调研发现需客户确认后才能用于正式报告 |

### 数据结构契约

v0.2.0 的项目数据结构：

## 交互设计

### 页面整体布局

- 横向四栏，从左至右依次为调研、分析、决策、执行，构成 OODA 循环（Observe-Orient-Decide-Act），各栏宽度比例约为 2.5:2.5:3:2。
- 各栏标题使用「动词 · OODA 阶段」格式（如「调研 · Observe」），栏内无「层」「区」字眼。
- 页面无横向滚动，四栏宽度自适应窗口，各栏内容过多时内部纵向滚动。
- 调研栏内部水平分为左右两个子区域：左半区为「业务理想」，右半区为「现实状况」，两区域之间有明显视觉分隔（不同底色加边框），仍在同一个「调研」标题栏下。两区域各自独立纵向滚动，便于对比期望与现实的差距。
- 页面底部保留一条可折叠的「示例线索」横条，跨栏示意关联关系。

### 调研

子区域结构：上半区为「业务理想」卡片列表，每卡为一条业务期望；下半区为「现实状况」卡片列表，每卡描述一个现状领域。两区域各自独立滚动，互不影响。移动端上四栏切换为单列纵向堆叠，子区域保持上下关系，卡片全宽展示。

卡片组件：内容为标题（干系人、场景或领域、维度）、简短正文、来源与确认状态。卡片右侧有勾选框供客户点击确认——理想卡片由顾问记录后需客户确认，现实卡片由顾问基于尽调填写，同样需客户确认事实准确性，确认后卡片视觉状态改变。每张卡片可长按，或桌面端拖拽、移动端长按菜单，关联到分析栏的某个洞察，也可标记为已对齐。

### 分析

洞察卡片组件：由矛盾陈述标题、证据链接标签（点击滚动并高亮对应的事实卡片）、根因文本、影响文本组成。卡片赋予一个或多个预定义聚类标签，标签可折叠分组显示。本栏顶部有「新建洞察」按钮，点击弹出内容填写面板，支持手动关联调研栏卡片。

聚类分组：分析层按聚类标签形成可折叠分组，默认全部展开，用户可切换显示全部或仅某类别的洞察。

### 决策

策略卡片组件：由策略名称、关联洞察（链接数量与标题概览）、我们的优势摘要、方案概要、资源与价格范围（含关键假设）组成。卡片底部是客户选择区，含「倾向本方案」勾选框和一个简短文本输入框，供客户填写顾虑或条件。

交互：客户直接在策略卡片的选择区操作，无需跳转，勾选后卡片高亮标示客户倾向。咨询团队可新建多个策略卡片并手动关联洞察，多个策略可同时勾选、支持标注优先级。

### 执行

任务卡片组件：由任务名称、关联策略（标签链接）、负责人或团队、截止日期、当前状态组成。任务卡片左侧使用状态标签（待开始、进行中、已完成、受阻），不同状态用不同边框或底色区分；每张卡片底部包含轻量进度条或状态更新时间戳。

交互：点击状态标签切换任务状态，受阻状态需填写受阻原因；任务卡片可关联决策栏的某个方案，点击跳转到对应策略卡片；支持拖拽调整任务优先级顺序。本栏顶部有「新建任务」按钮，支持填写任务信息并关联策略方案。

### 跨层联动

底部线索条默认折叠，点击展开显示一条横向串联的链条示意：调研 → 分析 → 决策 → 执行，匹配横向四栏布局。桌面端用连接线视觉引导，移动端调整为步骤指示条样式。

### 响应式行为

- 桌面端为横向四栏布局，各栏高度取窗口高度，无整体页面滚动。
- 移动端上四栏切换为单列流式布局，卡片维持全宽堆叠，确认勾选框与操作按钮调整为触控友好尺寸。
- 各栏内容较长时栏内独立滚动，无嵌套横向滚动。

### 视觉风格

- 整体采用低饱和度配色，以黑白灰为主色，避免鲜艳色彩干扰信息阅读。
- 标题栏使用浅灰背景加深色文字，不用彩色背景。
- 卡片边框为浅灰，选中或确认状态用深色边框或浅底色标示。
- 执行栏任务状态用灰度递进区分：待开始浅灰、进行中中灰边框、已完成深灰、受阻虚线边框。

## 质量保证

qtconsult 是咨询项目的信息看板。QA 的核心问题是：**看板上展示的信息，是不是准确反映了客户的真实情况？**

用例按三个业务实体组织：工作区用例覆盖进入系统、工作区切换与多租户隔离；项目用例覆盖看板展示、卡片操作与数据正确性；权限用例覆盖角色权限、数据可见范围与越权访问防护。

每条用例包含前置条件（进入场景前系统处于什么状态）、操作步骤（用户做了什么）和预期结果（用户应该看到什么）。

## 存储与运维

### 桶规划

| 桶 | 用途 |
|------|------|
| `qtconsult-provider` | 业务系统主桶，应用读写 |
| `qtconsult-archive` | 归档桶，多来源数据长期保存，兼顾灾备 |

### 首次部署

```hcl
resource "alicloud_oss_bucket" "provider" {
  bucket = "qtconsult-provider"
  acl    = "private"

  versioning { status = "Enabled" }
}
```

### 查看对象历史版本

```bash
ossutil list oss://<桶名>/<路径> --all-versions
```

### 误删恢复

```bash
# 用对象路径恢复最近一个被删的版本
ossutil restore oss://<桶名>/<路径>

# 或用版本 ID 恢复
ossutil set-acl oss://<桶名>/<路径> private --version-id <VersionId>
```

### 误改恢复

```bash
# 把指定历史版本下载到本地，再重新上传
ossutil cp oss://<桶名>/<路径> /tmp/restored --version-id <VersionId>
ossutil cp /tmp/restored oss://<桶名>/<路径>
```

### 归档策略

`qtconsult-provider` 通过同区域复制（SRR）同步到 `qtconsult-archive`，同时 `qtconsult-archive` 也接收来自其他业务系统之外的归档数据。

archive 内的数据按来源前缀组织：

| 前缀 | 来源 |
|------|------|
| `platform/` | 自建平台 |
| ... | 其他系统 |

```hcl
resource "alicloud_oss_bucket" "archive" {
  bucket = "qtconsult-archive"
  acl    = "private"

  versioning { status = "Enabled" }

  lifecycle_rules {
    id      = "archive-to-cold"
    enabled = true
    prefix  = ""
    transitions {
      storage_class = "Archive"
      days          = 90
    }
  }
}

# provider → archive（不同步删除标记，provider 删数据不影响归档）
resource "alicloud_oss_bucket_replication" "archive" {
  bucket = alicloud_oss_bucket.provider.id
  rules {
    status               = "Enabled"
    delete_marker_status = "Disabled"
    destination {
      bucket = alicloud_oss_bucket.archive.id
    }
  }
}
```

`qtconsult-archive` 不授予日常 DeleteObject 权限，防止误删蔓延到归档。
